每次搭博客都会经历同一个循环：兴致勃勃地挑框架、配主题、写下第一篇 Hello World，然后在第三篇之后彻底停更。复盘下来，问题不在写作欲，而在**维护成本**。

## 上一版踩的三个坑

### 1. 数据库是最大的负债

用数据库存文章，就意味着要维护连接串、备份、迁移，还要担心哪天免费额度到期。而我的全部数据量是——几十篇文章。为几十篇文章养一套数据库，属于典型的用大炮打蚊子。

### 2. 后台编辑器并不好用

我最终发现，比起在浏览器里对着富文本框敲字，我更愿意在 VS Code 里写 Markdown：能全文搜索、能 diff、能顺手贴代码块。

### 3. 部署链路太长

「本地写 → 提交 → 后台发布 → 触发构建 → 等 CDN 刷新」，任何一环出错都会让我把写作往后拖。而现在这条链路被压缩成了一件事：**git push**。

## 现在的方案

文章是仓库里的 `.mdx` 文件，构建时编译成静态 HTML，整站部署到 Vercel 的 CDN 上。整条链路只有三样东西：

| 环节 | 用什么 | 我要做的事 |
| --- | --- | --- |
| 写作 | MDX 文件 | 新建一个 `.mdx` |
| 构建 | `next build` | 什么都不用做 |
| 发布 | Vercel + Git | `git push` |

<Callout type="tip" title="这套方案最适合谁">
内容量在几百篇以内、不需要多人协作、不介意改样式要重新部署的个人站点。
如果你的博客需要评论审核、草稿箱、定时发布，那还是老实上现成的 CMS。
</Callout>

## 我特意保留的两个「不」

- **不加数据库**：需要结构化数据时，先用 YAML frontmatter 顶着。
- **不加客户端状态**：整站目前没有一个 `'use client'`，全靠服务端渲染 + CSS。

第二条带来的好处很直接：没有业务组件需要水合，深色模式也不用写一行 JavaScript（直接用 `prefers-color-scheme`）。

<Callout type="warn" title="但别指望 JS 体积归零">
框架自带的运行时（React + 路由）照旧会下发。实测这个站的文章页一共 7 个 chunk、
原始 562 KB、gzip 后约 173 KB——这是 App Router 的起步成本，和页面里写了多少业务组件无关。
「没有 `'use client'`」省掉的是**你自己那部分**代码，不是框架那部分。
</Callout>
